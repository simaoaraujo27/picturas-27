# Auditoria dos testes que falham

Estes 13 testes ficam fora de `make test` e `make test-all`, mas continuam executáveis por `make test-known-failures`. Todos reproduzem uma diferença entre a expectativa escrita no teste e a aplicação atual. Quando o PDF define uma regra, o teste segue-a; nos restantes casos mantêm-se as expectativas de produto e qualidade já assumidas antes desta revisão. O silêncio do PDF sobre um comportamento não invalida a expectativa do teste. `FAIL` na checklist é o resultado da asserção.

| Caso | Avaliação | Fonte da expectativa e evidência observada |
| --- | --- | --- |
| AUTH-02 — perfil de outra conta | **Assunção mantida:** perfis de outras contas são privados. O PDF de vídeo não altera esta expectativa. | `GET /users/{id}` devolve 200 e dados de outra conta. A API não exige token nessa rota. O teste espera 401/403 para preservar o isolamento entre contas. |
| AUTH-03.1 — alterar email | **Falha face ao contrato da aplicação.** O PDF de vídeo não altera esta expectativa. | O frontend envia `name` e `email` em `PUT /users/{id}` e a rota declara aceitar ambos. Responde 204, mas o login com o novo email devolve 401. O teste pára nesse ponto, antes de confirmar o nome. |
| AUTH-03.4 — apagar conta | **Falha face ao contrato da aplicação.** O PDF de vídeo não altera esta expectativa. | A rota declara apagar a conta e dados associados e chama a limpeza dos projetos. Após 204, o projeto continua em MongoDB. O teste pára nessa primeira falha, sem concluir se o original também permanece. |
| AUTH-04 — socket sem token | **Assunção mantida:** eventos de um projeto privado exigem acesso ao projeto. O PDF não define `project-op` especificamente. | Um socket sem token consegue juntar-se à sala pelo ID e recebe o evento privado. O teste confirma primeiro a entrega ao dono. A ausência de uma regra específica no PDF não torna o evento público. |
| AUTH-04 — socket de outra conta | **Assunção de segurança mantida**, com a mesma expectativa de isolamento do projeto. | Um utilizador autenticado sem acesso ao projeto recebe `project-op` depois de enviar `join-project` com o ID. Não prova que consiga editar o projeto nem receber o ficheiro de vídeo. |
| STORE-01 — URL direta do vídeo | **Incumprimento alinhado com `REQ-VID-ACCESS-001`** no Compose atual. | A porta 11000 está publicada no host; sem autenticação, `/image/public/.../src/{chave}` emite um URL assinado e esse URL descarrega o vídeo (200). O teste conhece a chave por preparação controlada; não demonstra que a chave seja adivinhável. |
| UP-01 — PNG corrompido | **Assunção mantida:** um upload com extensão PNG e conteúdo inválido deve ser recusado. O PDF trata explicitamente da validação de vídeos, sem contrariar esta regra para imagens. | O endpoint de imagem devolve 204 para bytes que não são um PNG. O teste falha ao verificar o código e não chega a confirmar se o item foi guardado. A rejeição de vídeo no endpoint de imagem continua na suite principal. |
| EDGE-01 — nome Unicode | **Assunção mantida:** nomes Unicode devem regressar sem alteração. O relatório exige nomes únicos e não contraria esta expectativa. | O nome `imagem teste ç.png` é devolvido com codificação alterada. A rejeição de nomes duplicados continua na suite principal. |
| PLAN-02 — cancelar vídeo | **Incumprimento explícito de `REQ-VID-CANCEL-002` (Should)**, já assinalado como não implementado no PDF. | Depois de reservar uma operação e cancelar, não há resultado parcial, mas a quota continua com uma operação consumida. O teste verifica as duas pós-condições. |
| PROJ-02/STORE-02 — apagar projeto só de imagens | **Comportamento herdado descrito no relatório**, sem confundir com a regra nova para vídeos. | O PDF diz que na solução de base apagar um projeto retirava o media; `UC-VID-001/FA11` e `RN8` mantêm **vídeos** na biblioteca. O teste usa `pattern.png`: o projeto desaparece de MongoDB, mas a imagem original continua a ser descarregada. Não testa vídeos. |
| PIPE-02 — dimensões nulas em vídeo | **Incumprimento explícito de `REQ-VID-FILTER-005` (Should)**, já assinalado como não implementado no PDF. | O teste reproduz o exemplo do relatório: vídeo, perfil premium e resize `1280×0`. Aceita rejeição ao adicionar a ferramenta ou ao aplicar, desde que ocorra antes do worker. Atualmente a API aceita o pedido de processamento com 201. |
| ASSIST-02 — falha de URL do preview | **Assunção técnica mantida:** falhas após criar um preview não devem deixar objetos órfãos. O assistente não é detalhado neste PDF. | Com falha injetada ao assinar a URL após o upload, o handler devolve sugestões mas não chama a remoção do preview; a chave também não é devolvida ao cliente. É um objeto potencialmente órfão. |
| RUN-03 — reinício do RabbitMQ | **Assunção de resiliência mantida:** um worker deve recuperar o consumo depois do reinício do broker. O PDF especifica explicitamente a religação do **gateway WebSocket** em `T-05`, mas não nega a expectativa para outros consumidores. | Num ambiente isolado, o worker conclui um primeiro vídeo, mas não reaparece como consumidor nos 90 s após reiniciar o broker. Os 90 s são orçamento do teste. O segundo trabalho não é enviado, logo não se provou perda de trabalho. |

Os testes estão em `tests/known_failures/api.test.js` e `tests/known_failures/resilience.test.js`. O runner guarda JUnit e logs em `tests/reports/`, regista a execução na checklist e limpa apenas as contas criadas pelo teste. O comando devolve código diferente de zero enquanto estes casos falharem. Se a regra de produto mudar explicitamente, o teste e o cenário da checklist devem ser atualizados; se o comportamento for corrigido, o teste deve voltar à suite principal.
