# Checklist de regressão global

Este é o catálogo global de comportamentos. `docs/TEST_PLAN.md` contém o plano de implementação, `tests/README.md` os comandos e `tests/TEST_EXECUTION_PROTOCOL.md` as regras obrigatórias para registar execuções feitas por IAs. Os testes que falham estão auditados em `tests/KNOWN_FAILURES.md` e fora dos totais da suite principal; nos casos não especificados pelo PDF mantêm-se as expectativas anteriores. A última falha de cada caso permanece visível. Os IDs são estáveis: quando um cenário é dividido, usar sufixos como `AUTH-03.1`.

**P0** bloqueia a entrega; **P1** cobre funcionalidades importantes; **P2** cobre variantes e limites. Registar **Cobertura** (`Inexistente`, `Parcial`, `Completa`) separadamente da **Última execução** (`PASS`, `FAIL`, `BLOCKED`, `Não executado`). `BLOCKED` significa que ambiente ou dependência impediu a execução. Uma suite aprovada não prova cobertura completa: `PASS` indica que os testes executados passaram, mesmo quando a cobertura do requisito é `Parcial`. Em cada execução registar data, commit, ambiente, executor, passos/comando e ligação a evidência.

Os testes existentes estão integrados no runner. Organizar casos novos por área dentro de cada categoria quando houver volume suficiente. Usar `tests/fixtures/{images,videos,invalid}/` para dados previsíveis e `tests/reports/` para evidência; não criar pastas vazias apenas para representar esta estrutura.

## Asserções e qualidade dos testes

- **Imagem:** verificar formato e dimensões com decoder, item de origem, contagem de resultados e propriedade específica do efeito (por exemplo, brilho médio ou região cortada), com tolerância explícita. Confirmar original intacto.
- **Vídeo:** verificar com ffprobe codec H.264, duração com tolerância explícita, resolução e áudio quando existe; descodificar frames de amostra para verificar o efeito. Confirmar original intacto e preview limitado a 3 s.
- **Extração:** verificar contagem, IDs únicos, origem, formato e distribuição temporal dos frames; a contact sheet deve refletir a linha temporal editada.
- **Falhas:** verificar ausência de resultados parciais, estado final, quota e erro visível. Evitar hash de ficheiros comprimidos quando encoders podem gerar bytes diferentes para conteúdo equivalente.
- Cada teste deve ter asserções sobre o comportamento, não apenas HTTP 200 ou existência de ficheiro. Cada fluxo crítico precisa de um cenário negativo. Para componentes P0, verificar pontualmente que uma alteração intencional do comportamento faz o teste falhar; considerar testes de mutação quando compensar.

## Matriz de combinações e riscos a validar

Não multiplicar todos os perfis × formatos × ferramentas × browsers em todos os testes. Cobrir cada regra isolada em testes rápidos e escolher combinações representativas nos percursos completos: anónimo/imagem, gratuito/imagem avançada no limite da quota, gratuito/vídeo com áudio, premium/vídeo longo, projeto misto com efeitos comuns e exclusivos, partilha read/edit. Para cada ferramenta, ter ao menos um caso válido e um inválido na camada mais barata que a verifica. Para os efeitos de imagem duplicados no worker de vídeo, comparar propriedades do resultado nas duas vias com uma fixture comum.

Verificar ainda os limites 0, 1, máximo e máximo+1 para duração, tamanho, resolução, fator de velocidade, trim, contagem/intervalo de frames e número de presets. Usar relógio controlado para quota diária e contratos de eventos; não usar sleeps fixos nos testes assíncronos. Os limites de tempo/performance só são critérios de aprovação depois de fixar hardware, dataset e orçamento.

**Resultados de execução:** ver `docs/TEST_RESULTS.md`. Foram confirmadas falhas de autorização, validação, limpeza e recuperação. `Completa` descreve a cobertura do cenário delimitado, não ausência de bugs. As lacunas nas linhas `Parcial` continuam explícitas; executar todos os testes implementados não equivale a testar todas as variantes possíveis.

## Ordem de execução

1. Em cada alteração: `make test-unit` e suites relacionadas.
2. Antes de integrar: `make test` (Node, Python, API e E2E).
3. Antes de entregar: `make test-all`, incluindo resiliência em containers descartáveis e performance limitada no ambiente local de teste.
